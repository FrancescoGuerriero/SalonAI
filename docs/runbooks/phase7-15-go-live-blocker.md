# Phase 7.15 Go-Live Blocker Runbook

## Rule

Do not run the production deployment workflow while any Phase 7.15 readiness
check is pending or failed.

## Common blockers

### Phase 7.14 is not merged

Wait for pull request #10 checks to finish and merge it into `main`. Re-run the
package launcher. The launcher uses `git merge-base --is-ancestor` and refuses
to continue when the required commit is absent from `origin/main`.

### Credential rotation is pending

Rotate the exposed MongoDB credential at the real provider. Revoke the old
credential. Generate a new JWT signing secret and invalidate runtimes using the
old value. Record the completion outside tracked repository files, then update
the readiness input confirmations.

### GitHub production environment is missing

Create the repository environment named `production`. Configure required
reviewers and environment protection rules. Add only the secrets and variables
required by the production workflow.

### GitHub-hosted SSH transport is unavailable

Configure `PRODUCTION_HOST`, `PRODUCTION_USER`, `PRODUCTION_SSH_KEY` and
`PRODUCTION_KNOWN_HOSTS` in the protected `production` environment. Keep strict
host-key checking enabled and use only the restricted `salonai-deploy` account.
A persistent GitHub Actions runner must not be installed on production.

### DNS does not resolve correctly

Create or correct the production A record. Enter the expected public IP in the
readiness input file. Wait for DNS propagation and repeat the readiness check.

### TLS files are missing

Install `fullchain.pem` and `privkey.pem` in the configured TLS directory. Keep
private keys outside Git and restrict file-system permissions.

### Release manifest is invalid

Use the manifest generated by the approved semantic release workflow. It must
contain exactly three services: `ai-service`, `backend`, and `frontend`, each
using an immutable `ghcr.io/...@sha256:...` reference.

### Compose rehearsal fails

Do not start containers. Inspect `.env.production`, the release manifest, TLS
paths, Docker availability, and the production/observability Compose files.
Re-run the non-destructive rehearsal only after correcting the cause.

## Recovery

The readiness scripts do not deploy or replace containers, so rollback is not
normally required. When an existing `.env.production` file is replaced with
`-Force`, the previous file is copied to an ignored timestamped backup directory.
