# DEV1 — Core module MongoDB acceptance extension

This extends the existing ephemeral MongoDB 7 CI suite established in PR #606. It uses the **same dedicated loopback-only acceptance database** and never connects to live tenant data.

## Verified in the CI fixture

- **Appointments:** existing business and selected-location appointment metric isolation; RBAC tests for required location context.
- **Service Catalogue:** actual management controller/Mongoose queries return only the trusted business's services, including exclusion of legacy unowned services. LocationServiceOffering records are read separately for each location and effective prices resolved through the canonical service configuration engine.
- **Workforce:** Mongoose queries generated by `scopedWorkforceFilter` return only staff belonging to the trusted business and allowed locations. Resource authority rejects foreign business and unauthorised location records.
- **Commerce / Inventory:** the canonical Product model has Business/Location fields; an inventory location filter restricts real product queries. **Not accepted:** legacy `commerceService.listProducts` still reads the global product catalogue without a trusted Business filter. The test deliberately detects both businesses in its result as regression evidence of the unresolved gap. Canonical Order has no Business ownership field; order endpoint tenant isolation is **not accepted**. This must be fixed in a separate reviewed implementation before enabling Commerce in multi-tenant production.

## Important boundaries

Tests use actual MongoDB collections and some real controller/service functions; they are **not HTTP end-to-end acceptance tests** for every module. Permission middleware tests exercise the canonical effective-authority scope rules, but do not simulate full user login or provider callbacks. A successful CI fixture never changes the Module Management dashboard's production acceptance status.

Next DEV1 slice: canonical Commerce ownership and tenant-scoped read/write enforcement for Products and Orders, with full authenticated HTTP and cross-tenant tests; no rollout until verified. Avoid auto-backfilling or reassigning production orders.

No production database access, module activation, external provider enablement, or monthly AI quotas.
